# TaskService release operations

A merge of the Publisher workflow runs the read-only application and capacity checks. Manual runs on Publisher main offer a backup rehearsal and a release. The release resolves its source from the chosen merged TaskService PR, checks its tree against the current integration branch, and requires successful CI for that exact head. Builds run on GitHub.

The supported off-host recovery adapter uses a mounted network filesystem. Configure the actual approved destination and recovery identity on the host in root-owned `/etc/taskservice/release.env` (0400 or 0600). The four settings are `TASKSERVICE_BACKUP_MOUNT`, `TASKSERVICE_BACKUP_DIR`, `TASKSERVICE_AGE_RECIPIENT`, and `TASKSERVICE_RECOVERY_IDENTITY`. The last setting is the path to a securely provisioned age identity accessible during the rehearsal. Keep an independent recovery copy outside Publisher. The adapter checks the live mount to prevent accidental fallback to local disk.

A rehearsal streams an encrypted PostgreSQL dump and Data Protection key archive to that destination, decrypts and checks the key archive, restores into a uniquely named disposable database, checks the migration history and runtime row-level permissions, and removes the rehearsal database. A successful backup directory includes checksums and a RESTORE_VERIFIED timestamp. In a disaster, recover the database to a separate target with matching DB roles and restore the key archive to an isolated Data Protection volume under the existing application UID. Validate protected records, tenant access and quarantined files before redirecting traffic.

Release takes its own fresh backup and repeats the rehearsal before running the supplied EF migration. Existing host-specific Compose and secret files supply configuration. The API and worker receive the same image. The readiness check covers TaskService and the co-hosted Publisher. A real public browser opens the customer portal and verifies anonymous access restrictions. An application failure restores the previous image configuration. Schema and data remain in place for a forward fix. Only ship migrations whose running predecessor tolerates the expanded schema. A destructive schema change needs its own cutover and reconciliation procedure.
